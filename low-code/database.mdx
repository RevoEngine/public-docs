Use the structured query API for most reads and writes. It provides explicit fields, filters, grouping, sorting, pagination, and JSON-path behavior without assembling SQL strings.

## Read rows

```js
const response = await api.getDatabaseData('orders', {
  fields: ['orderId', 'customerId', 'amount', 'createdAt'],
  filter: {
    and: [
      { field: 'status', op: 'eq', value: 'CONFIRMED' },
      { field: 'amount', op: 'gte', value: 100, filterType: 'number' },
    ],
  },
  sort: { createdAt: 'DESC' },
  take: 100,
});

return { rows: response.data, next: response.next };
```

Prefer a narrow field projection. `getDatabaseData()` accepts an explicit non-negative `take` (maximum 100,000) or `take: null` for a bounded 2,000-row page. Omitting `take` (or the query) also defaults to 2,000 rows and logs one warning per execution; specify `take` deliberately. Use `walkDatabaseData()` with `fullScan: true` for a complete scan. Do not page through a large table with `skip += 200`.

For one matching record, use `getDatabaseDataRow(name, query)`. It returns the row or `null` in one database operation, without a collection wrapper. Omit `take`, `skip` and `count`; add `sort` when several rows match and the chosen row matters. `tx.getDatabaseDataRow()` supports row locks within a transaction.

```js
const customer = await api.getDatabaseDataRow('customers', {
  filter: { field: 'customerId', op: 'eq', value: customerId },
});
if (!customer) api.throw(404, { message: 'Customer not found' });
```

## Process large results

Use `walkDatabaseData()` for a Job that processes many rows. Specify either a non-negative `take` or `fullScan: true`; a missing `take` does not silently scan the whole table. The default `batchSize` is 2,000 (accepted range: 2,000–10,000). Each non-final callback receives exactly that many rows if available, and callbacks are awaited sequentially.

```js
const result = await api.walkDatabaseData(
  'orders',
  { fields: ['orderId', 'status'], filter: { field: 'status', op: 'eq', value: 'NEW' }, take: 100000 },
  async (batch) => {
    await api.upsertDatabaseData('order_export', batch, { return: false });
  },
);

return result; // { processed, batches }
```

Process each batch before the next one arrives; do not accumulate every row in an array. Use `fullScan: true` only when processing until the end is intentional. A single wide row can still be expensive: select only the columns needed. Jobs remain subject to their timeout and resource limits. The walker targets PostgreSQL-backed databases. For complex sorting or joins, it uses a cursor; its `auto` strategy chooses keyset pagination only when the query shape is safe for it. There is usually no need to select a strategy manually.

For a count without loading rows, use one call:

```js
const total = await api.countDatabase('orders', {
  filter: { field: 'status', op: 'eq', value: 'NEW' },
});
```

Database operations beyond 1,000 calls in one execution are logged and throttled; prefer bulk writes and the walker over repeated small reads. Direct `getSecret()` / `getSecrets()`, Storage, Files, Agent and orchestration calls are outside this database throttle. Database-backed `getInstanceData()` sources are included.

## Mutate rows

Use the dedicated insert, upsert, update, and delete methods. Bulk update and delete accept the canonical structured filter tree.

### Partial updates are the default

`api.updateDatabaseData()` updates one row identified by its primary-key object.
Put only the properties that change in `newObject`; omitted and `undefined`
properties are preserved. A present `null` deliberately clears a nullable property.

`api.upsertDatabaseData()` follows the same PATCH rule on a primary-key conflict.
It creates a missing row from the supplied data, but when the row already exists it
changes only properties present in that input object. Do not fetch a full row merely
to change one property.

```js
await api.upsertDatabaseData(
  'orders',
  [{ orderId: 'order-1', status: 'QUEUED' }],
  { onlyKeys: true },
);
```

The third argument controls the response for both `insertDatabaseData()` and
`upsertDatabaseData()`:

| Option | Default | Meaning |
| --- | --- | --- |
| `return` | `true` | Return the written rows. Set `false` when the rows are not needed. |
| `onlyKeys` | `false` | With `return` enabled, return only primary-key fields. |
| `patch` | `true` for upsert | Preserve properties missing from a conflicting upsert row. Set `false` only to request legacy full replacement on conflict. It is not valid for insert. |

For a multi-row PATCH selected by a structured filter, use
`api.updateDatabaseDataRequest()`:

```js
await api.updateDatabaseDataRequest(
  'orders',
  { filter: { field: 'status', op: 'eq', value: 'NEW' }, take: 1000 },
  { status: 'QUEUED' },
);
```

## Transactions

Use `api.transactionDatabase()` for check-then-write workflows that must commit together.

```js
const created = await api.transactionDatabase(async (tx) => {
  const customerId = api.input('customerId');
  const existing = await tx.getDatabaseData(
    'customers',
    { filter: { field: 'customerId', op: 'eq', value: customerId }, take: 1 },
    { lock: 'update' },
  );

  if (existing.results === 0) {
    await tx.insertDatabaseData('customers', [{ customerId, status: 'ACTIVE' }]);
  }
  return existing.results === 0;
});
```

Await transaction calls sequentially. Keep sleeps and remote HTTP/SFTP side effects outside the callback because a transaction reserves a connection and may hold row locks.

## Raw SQL

`api.queryDatabase()` is for parameterized `SELECT` or `WITH` reads when the structured builder cannot express the query. Use the mutation helpers for writes.
