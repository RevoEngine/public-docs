An approved terminal lets an Interactive Agent run commands in a connected macOS or Linux environment. The runner can be your computer or a virtual machine running the RevoEngine CLI. The owner approves the terminal before a conversation can use it. Commands run with the runner's operating-system account; its permissions remain an outer limit.

## Connect a workspace

1. Install the [RevoEngine CLI](/developers/cli) on the runner and sign in with a personal API key.
2. Choose an existing directory and run `revo terminal connect --workspace "$HOME/projects/my-project" --name "Work VM"`.
3. Open **Settings → Vault → Terminals** in the browser and approve the pending terminal. **Workspace Access** is the default command permission. CLI pairing alone does not authorize commands.
4. Keep the CLI connection running, or install its per-user background service. An Assistant can use an approved online terminal and its approved workspaces directly; you do not need to pair it again for each chat.
5. Describe the outcome you want. The Assistant can run workspace commands, inspect output, edit files, install packages and run tests within the permission boundaries below.

The owner can share an approved terminal with selected users, groups, or the instance. Sharing does not change the runner's operating-system account. A conversation can use multiple approved terminals; its activity shows which runner handled a command.

### One device, several workspaces

The CLI keeps a stable device registration across restarts. Connecting another directory with the same CLI profile and terminal name registers an additional workspace on that device. Approve it in the terminal's **Workspaces** settings. Each workspace has its own access and sharing contract, bounded by the device permissions. An already-running device refreshes this contract without a second runner process. Preserve the CLI registration to keep using the same device; restarting the terminal does not itself require a new owner approval.

The temporary or whole-thread permissions below apply to the selected chat, device and workspace. A permission for one workspace does not authorize another. If older duplicate registrations make the name ambiguous, select the intended registration explicitly with `--terminal-id`.

## Permissions

Terminal permissions have two independent controls in **Settings → Vault → Terminals → Permissions**. The owner can change either setting while the runner is connected. The runner checks the current grants before each dispatch and stops work that loses required access. The terminal's **Full Access** command setting is separate from the Composer permission mode with the same name.

### Commands

| Setting | Access |
| --- | --- |
| **Workspace Access** (default) | Runs ordinary commands, builds, tests, and edits inside the selected workspace. Writes outside it and host-level actions are blocked unless you approve an exception. |
| **Workspace Access with a temporary exception** | Keeps Workspace Access as the saved setting. An approval permits the requested host-level action once, or permits host-level actions in this chat on this terminal and workspace for 15 minutes, one hour, eight hours, 24 hours, or the current thread. The approved host action can access files outside the workspace. |
| **Full Access** | Allows the Assistant to explicitly request host-level commands without another command-scope approval. Those commands can read, change, or delete anything the runner's operating-system account can access, including files outside the workspace. This setting does not grant network access by itself. |

### Networking

| Setting | Access |
| --- | --- |
| **No Network** | Commands and Browser cannot connect even to localhost unless you approve a temporary network exception. |
| **Local Access** (default) | Permits supported connections to services on the runner's localhost. Internet and other LAN hosts require a temporary network exception. |
| **Full Network Access** | Permits connections to addresses the runner can reach, including the internet and LAN, without another network-scope approval. It does not grant access to files outside the workspace. |

The Assistant requests the command scope and network scope needed for each action. A broader saved grant does not automatically turn an ordinary workspace command into a host command or add network access. For example, **Workspace Access + Full Network Access** can download dependencies and write inside the workspace, but cannot write elsewhere. **Full Access + No Network** permits a requested host-level command to access files available to the runner account, while blocking its network connections. A temporary exception can broaden either dimension without changing the saved settings.

### How the sandbox works

The **workspace** is the directory selected when connecting the CLI runner. Commands execute on that computer or VM, not in a separate RevoEngine-hosted filesystem. For a workspace command, the runner checks the working directory and launches the process with operating-system-enforced file and network restrictions. It can write in the workspace and a temporary working area; the restrictions block writes elsewhere. It can also read the system and toolchain files needed to run programs, so Workspace Access is not a promise that every file outside the workspace is unreadable. Files reached through links remain subject to the boundary. Child processes inherit these restrictions.

On macOS, supported workspace shell actions can connect to localhost under **Local Access**. On Linux, the workspace shell remains isolated from host localhost; the local Browser action is available. Host commands with **Local Access** are unavailable on Linux until that boundary can be enforced. If the runner cannot enforce a required boundary, it rejects the action. Browser actions have their own controlled execution path and follow the networking grant.

**Full Access** removes the workspace file boundary for a host-level command; it does not elevate the runner's operating-system account. Use a dedicated account or VM if the runner has access to other projects, personal files, or credentials. With **Full Network Access** as well, a host-level command can reach external services and transmit data available to that account.

## Approvals for elevated actions

The Assistant explains why an action needs host-level commands or more network access. Under **Restricted** Composer, you decide directly. Under **Auto Review** or **Full Access**, RevoShield first assesses the exact action against your request and sends it to you if it cannot safely approve it. A saved Full Access command grant or Full Network Access grant covers its own dimension regardless of Composer mode. Destructive commands and secret access may still require separate review.

When your decision is needed, you can approve the exact invocation once or grant the missing command or network scope for **15 minutes**, **one hour**, **eight hours**, **24 hours**, or **this thread** on this chat, device and workspace. A timed grant does not change the terminal's permanent settings or authorize a different action after a one-time approval. It ends at expiry, explicit chat disconnect, or a change to the grant. Whole-thread consent has no time expiry, survives later messages and short reconnects, and ends on explicit disconnect, thread deletion or a grant change. It is not copied to a forked chat. A short runner reconnect can preserve a still-valid permission for the same chat, device and workspace. The runner checks authorization again before input or another action; work requiring an expired or revoked scope is stopped.

The approval shows the proposed command or Browser action and the reason for elevation. Terminal activity in the conversation shows the runner, command, output, and execution status. Ordinary workspace actions within the available grants do not create an approval prompt for every read, edit, or test.

<Warning>
  Full Access gives a requested host-level command broad control over everything the runner account can access. It can modify or delete files outside the workspace. Full Network Access can contact external services. Review the requested scope and destination when an approval reaches you. A terminal grant does not expand operating-system permissions.
</Warning>

## Work with running commands

The Assistant starts a command and waits briefly for its result. A long-running command remains visible under its execution ID; its shell output and final status update in the conversation even if the Assistant continues with other steps. It can check status, cancel, send input, and resize a PTY for interactive programs. An ordinary command may run for up to 59 minutes. A compatible runner can keep an explicitly requested background process running without that fixed command deadline, while its authorization and runner remain valid. Startup output is not proof that a development server is ready; the Assistant should verify its URL. Several commands may run at once, subject to runner limits.

If the runner's connection drops, the CLI retries temporary transport or dependency failures and resumes the same execution without starting the command again. Recovery has a three-minute window; unsuccessful reconnects do not restart that window. Authentication failure or confirmed revocation stops recovery. If a dispatched operation has no confirmed outcome, inspect its status and target before repeating a command with side effects. A reconnect alone does not prove that the operation completed.

The Assistant can request a connection refresh while the CLI remains running. Recovery can continue through renewed permission or a clarification when user action is required. It cannot wake a stopped CLI or reconstruct processes that ended when the CLI stopped. Internal status checks are omitted from the visible activity list; the original command still shows its progress and outcome.

The Assistant can apply a workspace patch without asking for each ordinary edit. Browser actions can navigate to an HTTP(S) page, inspect visible page text, interact with forms, and take a screenshot. The CLI installs the required browser runtime; a separate browser installation is not required. The activity shows the visited URL and page output; a screenshot is automatically attached and shown in the Assistant conversation. The Assistant loads its pixels only when visual inspection is needed. Browser access follows the terminal's network grant and any temporary exception. For a password or similar secret field, the Assistant can request a secure input popup: the value goes directly to the connected browser session and is not included in the model-visible tool call. The Assistant must inspect the resulting page to confirm the action. The browser runs as a dedicated controlled action, separate from the shell's operating-system sandbox.

### Browser state and limits

Browser tabs and cookies belong to the current chat, device and workspace. They survive later messages and short connection recovery while the runner and browser remain alive. A session expires after one hour without browser activity. The runner allows four sessions and sixteen tabs per session. At capacity, the Assistant can inspect the permitted session inventory, identify its owning chat, and explicitly close unneeded tabs or sessions. It cannot inspect or close another user's sessions, and active sessions are not silently evicted.

Changing between **Local Access** and **Full Network Access** recreates the browser context and loses its cookies and form state. Choose Full Network Access before starting a login flow that uses remote authentication, APIs or assets, even when the initial page is on localhost. After a context change, the Assistant can inspect the remaining tabs, navigate again and request permission or secure credential input when needed. Closing a session, stopping the CLI, browser failure or loss of authorization can also destroy its state. A one-time network exception closes its browser context after that action; use a timed or whole-thread permission for continued browsing.

Slow pages can use an explicitly increased browser action timeout, up to two minutes. This changes the wait for that operation; it does not extend permissions or automatically repeat a click or submission.

To show images created by a command or browser screenshot, the Assistant can use `save_image` with up to 32 PNG, JPEG, or WebP files per call from the workspace (240 MiB total per call). It can make more calls for a larger collection. The runner uploads them securely; RevoEngine then attaches them to the conversation. The Assistant loads their pixels in the next model step only when it explicitly needs to inspect them. `save_image` requires **Full Network Access** or a temporary full-network exception.

If a side-effecting command has an uncertain outcome after recovery, inspect its status before trying it again. Starting it twice could repeat its effects.

## Transfer workspace files

On a compatible runner, the Assistant can upload an authorized workspace file to Storage or download a Storage file into the workspace. File bytes travel directly between the runner and managed Storage using a short-lived upload or download URL; the terminal connection carries control and completion metadata. Full Network Access or its approved exception is required. Treat transfer URLs and their required headers as credentials and keep them out of source files and logs.

An upload must finish before its Storage upload session is finalized. Resumable uploads can continue from the confirmed committed offset; an uncertain write must be checked before retrying. Downloads use a temporary file and become visible at their destination only after successful completion. Existing files are preserved on failure and overwritten only when explicitly requested. Transfers have a 90-second idle timeout, rather than a short fixed total duration. Permissions, URL validity, available disk space and runner lifetime still limit a long transfer.

## Keep a terminal available

The foreground `revo terminal connect` command works while the CLI runs. A terminal can remain registered for months, but live command and browser state depends on the running process. Presence and last-online time describe connectivity; they do not grant access or create a configuration version. Configuration changes have their own revision and Activity history. After approval, you can install a per-user background service on macOS or Linux:

```bash
revo terminal service install --workspace "$HOME/projects/my-project"
revo terminal status
```

Use the same CLI profile to manage the device service. The service remains associated with the device's original service directory even when it serves several registered workspaces. Newly installed services restart eligible failures and stop after fatal authentication or revocation errors. Reinstall an existing service to adopt the updated supervisor behavior. A background service keeps the runner available; it does not make browser cookies or ordinary command processes durable across a runner restart.

## Disconnect and revoke

Disconnecting a runner from one conversation removes that conversation's connection. It does not revoke the owner's terminal grant or stop an already-running process. The owner can remove the terminal in **Settings → Vault → Terminals** to revoke its grant. To remove a locally registered runner, stop its background service first if installed:

```bash
revo terminal service uninstall --workspace "$HOME/projects/my-project"
revo terminal disconnect --workspace "$HOME/projects/my-project"
```

The terminal settings and conversation show activity for authorized viewers. A pending request or offline runner cannot execute commands. An approved online workspace can establish its conversation connection automatically.
