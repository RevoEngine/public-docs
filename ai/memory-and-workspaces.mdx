RevoEngine keeps three kinds of state separate. This makes Agent behavior easier to understand, govern, and resume:

| Store | Purpose | Examples |
| --- | --- | --- |
| Thread or run state | Continue active work | Messages, current goal, plan, approvals, action results, checkpoint |
| Memory digest | Reuse concise, stable knowledge | User preference, Agent convention, workspace-specific operating context |
| Workspace | Store durable files | Reports, source files, generated artifacts, review material |

Personal preferences and instance-wide policy are configuration, not memory. See [Agent configuration and personalization](/ai/assistant-configuration).

## Conversation and run continuity

An Interactive Agent thread keeps the messages, plans, approvals, actions, and artifacts needed for the current collaboration. An Autonomous Agent run additionally keeps durable lineage and checkpoints so authorized work can continue after a pause, retry, or scheduled wake-up.

Use this state for live progress. Do not copy every intermediate action into memory.

## How runtime memory works

Runtime memory is a bounded digest of stable knowledge. RevoEngine can provide at most one current digest for each active owner scope:

| Scope | What it represents | Example |
| --- | --- | --- |
| `USER` | Preferences and working conventions for one user | “Lead with validation results.” |
| `AGENT` | Operating knowledge for one Agent | “Reconcile settlement totals against the approved finance View.” |
| `WORKSPACE` | Context shared by work attached to one workspace | “Use the quarterly report template stored in this workspace.” |

The runtime can use these digests as soft context. They never override the current request, access controls, approval policy, verified action results, or the Agent definition.

Administrators can enable or disable memory, allow governed writeback, and set a bounded context budget. A larger budget can preserve more useful context, but it also increases model input and makes poorly maintained memory more expensive. Keep the digest compact.

## Memory writeback

When writeback is enabled, an Agent can propose a durable update when it discovers stable knowledge that will matter later. Updates are version-aware and use one of three operations:

- **append** — add a new durable fact or convention;
- **edit** — change a specific existing part;
- **replace** — replace the complete digest after loading its full current value.

If the digest changed after it was read, the update must be refreshed instead of silently overwriting newer knowledge.

Good memory is concise and remains useful after the current task ends:

```text
The finance reconciliation flow treats the approved settlement View as its source of truth.
Release summaries must lead with validation and rollback status.
```

Do not save credentials, access tokens, raw reasoning, full documents, transient task progress, or large action outputs. Store exact material in Storage and keep only the durable convention or reference in memory.

## Search and deeper recall

The digest is the normal runtime entry point. When a task needs older or more specific context, an authorized Agent can search or load governed memory records instead of placing the entire history into every model request.

This separation keeps the default context predictable while retaining a path to deeper recall.

## Agent workspaces

Every successfully created Autonomous Agent has a workspace root:

- **Managed** — RevoEngine creates and governs a dedicated workspace.
- **Existing** — an operator links an authorized Explorer folder as the Agent root.

The root is the default location for Agent-generated files and an enforced boundary for workspace operations. Linking an existing folder is an authorization decision: review its contents, service-account access, and ACLs before making it the Agent workspace.

Interactive Agents create ordinary Storage files under the current user's authorization. Autonomous Agents use their assigned service account and workspace policy.

## Workspace writes and approvals

Writes inside an enforced Agent workspace can proceed without an extra per-action confirmation when the configured policy allows them. Writes outside that boundary remain ordinary Explorer operations and keep their normal permission and approval rules.

The workspace boundary does not make content public. Upload, download, preview, archive, and folder operations still require authentication and authorization.

## Outputs and completion

Reference a generated file only after the platform has persisted it. A durable output can include its Storage entry, name, media type, kind, size, and source activity when available.

| The task asks for… | Correct completion |
| --- | --- |
| A durable report, export, or file | Persist the artifact and return its reference |
| A verified platform mutation | Return the result and operational evidence; a file is optional |
| Analysis or a concise answer | Return the answer directly unless an artifact was requested |
| Work that must resume later | Preserve run state or a checkpoint, not a fake memory note |

<Warning>
  Do not store secret values in memory, workspace guidance, generated reports, or Agent messages. Keep secrets in the RevoEngine Secrets service and expose them only through approved runtime bindings.
</Warning>
