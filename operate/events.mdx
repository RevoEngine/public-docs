Events turn a typed message into durable work. An Event definition says **which messages it accepts**, **which target receives them**, and **which filter must match** before RevoEngine schedules anything.

One Event definition has one target. Create several active definitions for the same type when one business signal must fan out to independent Jobs or Agents; Event History records which targets matched and which filters skipped delivery.

## When to use an Event

Use an Event when work should begin because state changed, not because a person called an Endpoint or a clock reached a particular time.

| Scenario | Event definition |
| --- | --- |
| Process a finalized Storage upload | `STORAGE_CREATED` → validation Job |
| Generate a preview after a Storage write | `STORAGE_CREATED` → rendering Job |
| Reconcile access after an identity change | `USER_UPDATED` → governance Job |
| React to a domain signal | `type: "ORDER_APPROVED", custom: true` |

<Tip>
  Publish small event envelopes and let the target load authoritative data by ID. Event metadata is searchable, but it is not a replacement for a Table or Storage object.
</Tip>

## Create an Event in the UI

Use [native Event types](/operate/event-types) for platform changes, or [publish a custom Event](/operate/event-publishing) for a business signal. Set [message filters](/operate/event-filters) for admission and [Runtime input](/operate/event-inputs) for the selected Job.

Follow [Run a Job from a custom Event](/examples/event-job) for the complete template, trigger and result workflow.

Open **Jobs → Events**, select **Add**, and configure the definition.

| Field | Required | Meaning |
| --- | --- | --- |
| Name | Yes | Operator-facing name used in lists and history. |
| Category | No | Presentation grouping for larger automation estates. |
| Description | No | Why the subscription exists and what it is expected to start. |
| Internal | Yes | Enabled for a platform lifecycle event; disabled for an application-defined event. |
| Type | Yes | Select a supported internal type, or enter the application event name when Internal is disabled. |
| Target type | Yes | `JOB_TEMPLATE` or `AGENT`. |
| Target | Yes | The Job template or Agent that receives matching work. |
| Delivery mode | Agent only | `INBOX` queues durable Agent work; `DIRECT_RUN` starts a run directly. |
| Activate upon creation | New definitions | Whether matching begins immediately. |
| Metadata | No | Searchable ownership, service, environment, or cost-centre labels. |
| Filter | No | Conditions evaluated against the normalized message. Empty means match all. |
| Runtime input | Job only | JSON object configured in **Options**; defaults to `{}`. |
| Input mode | Job only, through 1.8.0 | **Override** overlays Job defaults; **Deep Override** merges nested objects; **Replace** replaces the input entirely. Defaults to **Override**. |

For a Job target, the selected template carries the Component, execution principal, input defaults, limits, concurrency, and retry policy. For an Agent target, delivery uses the current Agent definition.

## Group Events into one Job

<Note>
  Job delivery modes and the trigger array are part of **RevoEngine 1.8.1**. The example below runs locally in your browser.
</Note>

In **Jobs → Events**, select a **Job Template** target and open **Delivery** and choose a **Mode**. **Single** is the default when the subscription has no grouping configured. You can configure grouping on a custom or native Event with a Job Template target. Schedules and Agent targets use their own delivery settings.

| Delivery | When the Job becomes eligible | Job input |
| --- | --- | --- |
| **Single** | After each matching event is admitted, or when a future-dated event becomes due. | One entry in `triggers` plus top-level `type`, `message`, and `metadata`. |
| **Batch** | When the group reaches **Maximum events** or **Maximum wait** from its first event, whichever comes first. | One entry in `triggers` per collected event. |
| **Debounce** | When the group reaches **Maximum events**, **Maximum wait** from the first event, or the **Quiet period** after the most recent event for that key, whichever comes first. | One entry in `triggers` per collected event, with every message retained. |

Batch and Debounce both keep every collected Event as a separate entry in the same `triggers[]` array, in admission order. Each entry keeps its own message, metadata, and input. A quiet period lets Debounce release a short burst before the maximum wait. For example, with a 120-second maximum wait and a 10-second quiet period, if the last change arrives at +6s and the size limit is still open, Debounce releases at +16s and Batch at +120s.

To process price lists independently, set **Grouping key path** to `/message/priceListId`. RevoEngine groups matching events by that JSON Pointer value within this subscription and its saved revision. Omitting the path groups matching events across the subscription. Strings, finite numbers, and booleans are valid keys. An event with a missing or non-scalar key is released on its own without waiting for a group. Set **Maximum events** to 2–100 and **Maximum wait** to 1–3,600 seconds. The quiet period can be at most the maximum wait.

The Platform API accepts the same settings under `delivery`. New definitions without `delivery` use Single. Set `delivery` to `null` to select Single on an existing definition.

```json
{
  "delivery": {
    "mode": "DEBOUNCE",
    "keyPath": "/message/priceListId",
    "maxSize": 4,
    "maxWaitSeconds": 10,
    "quietPeriodSeconds": 5
  }
}
```

The Job receives `api.input().triggers` in admission order. Each entry includes `triggerType: 'EVENT'`, the subscription’s `eventName` and `jobEventId`, the occurrence’s `eventHistoryId`, and its `type`, `message`, and `metadata`. The subscription’s Runtime input is available as `trigger.input`. Job Template defaults stay in `api.input().templateInputs`. A Job released by either grouping mode uses the trigger entries even when it contains only one Event.

A Schedule pointing to the same template runs separately and has its own trigger entry. Separate Event subscriptions stay separate even when they target the same template.

A group that would exceed 512 KiB of serialized trigger input is released before another group starts. A single event above the limit is delivered in its own Job. Future-dated Events are isolated until their scheduled time. Vault-bearing Events, native Job lifecycle Events and Assistant-originated Events also retain separate execution boundaries. Replays collect independently of live events. Event History links each occurrence to the shared Job after the group closes. Retries retain the original triggers, so make each side effect safe to repeat.

Use the same business field for [dynamic Job concurrency](/operate/jobs#limit-concurrent-jobs-per-key) to prevent two Jobs from processing one price list at the same time. Grouping determines which Events enter a Job. Concurrency determines how many eligible Jobs may run together.

## Operate configured Events

The **Jobs → Events** grid is the inventory of current and deleted definitions. It exposes name, category, description, active state, Internal classification, Type, target references, metadata, creation/update ownership, version, and deletion state. Every visible column can be used as an operator filter where its data type allows it.

Open a row to review the effective target, delivery mode, metadata, and filter before changing lifecycle state. The header links directly to **History**, so the definition and its observed deliveries remain separate:

| Definition action | Effect |
| --- | --- |
| **Activate** | Starts matching future messages after target configuration and instance quotas are revalidated. |
| **Disable** | Stops future matches; existing Event History and already scheduled targets remain. |
| **Run** | Custom definitions only: publishes a message under the stored type. Native lifecycle events are replayed from Event History. |
| **Update** | Replaces editable configuration with optimistic version checking. A stale editor is rejected. |
| **Delete** | Soft-deletes and disables the definition. |
| **Restore** | Makes a deleted definition available again; review target and filter before activation. |

Instance settings govern the total and active Event-definition quotas. An active definition whose target was deleted, disabled, or is no longer authorized cannot be admitted until that dependency is corrected.

## Incoming file → Event → Job → output

1. An operator, SDK, or Component uploads a file into the Storage **Files** workspace and finalization creates a `storageEntryId`.
2. `STORAGE_CREATED` records the entry projection as the Event message. A filter admits only the intended MIME type, folder policy, or user metadata.
3. The selected Job template starts its Component under the template's service account. The Job input contains `{ type, metadata, message }`.
4. The Component reads `api.input()?.message.storageEntryId`, validates authoritative entry metadata and content, and uses bounded `storage.getFileData()` batches.
5. It writes a result with `storage.putObject()` or a finalized upload session, then returns the operation ID and both Storage entry IDs.
6. Event History proves admission and target scheduling; Job History, logs, and the output Storage entry prove processing.

<Note>
  Grant the Job service account read access to the input's complete ancestor ACL chain and write access to the output folder. An Event matching successfully does not bypass Storage authorization at execution time.
</Note>

See the full [file-processing workflow](/platform/file-processing-workflow) for upload, schema, finalization, and retry-safe output design.

## Roles and lifecycle

| Action | Required role |
| --- | --- |
| List and inspect | `AUTOMATION_READ` or `AUTOMATION_ADMIN` |
| Run, activate, or disable | `AUTOMATION_RUNNER` or `AUTOMATION_ADMIN` |
| Create, update, delete, or restore | `AUTOMATION_ADMIN` |

Updates use a version field for optimistic concurrency. Deleting is recoverable; restoring returns the definition but does not imply that it should immediately be active. Review its target and filter first.

## Delivery and failure semantics

```text
event accepted
  -> durable Event history created
  -> active definitions resolved
  -> filters evaluated
  -> matching targets scheduled
  -> target identifiers recorded
```

Acceptance confirms that RevoEngine recorded the event; it does not mean every target completed successfully. Diagnose fan-out in Event History, then follow the related Job or Agent run for execution-level status.

Storage commits are not rolled back if post-commit lifecycle event enqueueing fails. Operators should therefore reconcile important ingestion sources against Storage entries as well as monitor Event History; the durable file remains the source of truth.

Redelivery of the same accepted occurrence reuses the recorded initial child Job for each Event definition. Two definitions targeting the same template still count as separate subscriptions. An operator Replay creates new occurrence history and can create new Jobs under current definitions and filters.

Targets that call payment, provisioning or messaging systems need a stable **business operation key**, such as `order-1:invoice:v1`, enforced at the side-effect boundary. A key based only on an Event history ID changes on Replay and cannot prevent the same invoice from being issued again. Compare [delivery guarantees](/patterns/delivery-guarantees) and [metadata and correlation](/patterns/metadata-and-correlation).

### Diagnose by boundary

<AccordionGroup>
  <Accordion title="The Event never appears in History">
    Confirm the producer used the expected type and the trigger request was accepted. Delayed Job-template targets should already be visible in Event History; inspect their `scheduledFor` and wait reason. For Storage workflows, also inspect the durable Storage entry because a committed file remains authoritative if post-commit event delivery fails.
  </Accordion>
  <Accordion title="History exists but the target was skipped">
    Compare the saved normalized message with the definition filter. Check data types as well as values: the number `10000` is not the string `"10000"` for exact equality.
  </Accordion>
  <Accordion title="The target was scheduled but failed">
    Continue in Job History or the Agent run. Event History owns admission and fan-out, while target history owns execution, permissions, retries, and result.
  </Accordion>
  <Accordion title="A custom event matches too many definitions">
    Use a more specific business event type or add message/metadata filters. Keep each definition responsible for one target so unwanted fan-out can be disabled independently.
  </Accordion>
</AccordionGroup>

## Production checklist

- Give custom types stable names and set `custom: true`.
- Filter before starting expensive work.
- Validate the payload again inside the target.
- Use a dedicated service account on Job templates.
- Correlate Event history with downstream operation IDs.
- Make every external side effect replay-safe.
- Disable the definition before changing a production target.
- Review configured definitions and active quotas periodically; remove obsolete subscribers instead of leaving ambiguous filters active.
