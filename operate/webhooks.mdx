Create an **outbound Webhook** when a partner should receive an HTTP request after your application responds. One Webhook record tracks the request and its separate delivery attempts.

<Warning>
  This workspace does not create inbound subscriptions. To receive a partner callback, publish an authenticated [Endpoint](/operate/endpoints), validate the request, and then create a Job or Event.
</Warning>

## Create a webhook in the UI

Open **Webhooks** and select **Trigger webhook**. The form exposes:

| Field | Required | Meaning |
| --- | --- | --- |
| Custom ID | No | Caller-provided UUID used as the Webhook ID. Creation rejects an ID already present; it does not return an existing successful result. |
| Maximum retries | No | Additional attempts after the initial delivery: `0` disables retries, a positive value caps retries, and `-1` permits retries while delivery remains retained. Omission inherits instance policy. |
| Save details | No | Retain request details for later inspection. |
| Stop on unauthenticated | No | Stop after an attempt returns HTTP 401 (`UNAUTHENTICATED`), even if retries remain. The API field is `stopOnStatuses: ["UNAUTHENTICATED"]`. |
| URL | Yes | Absolute `http` or `https` destination. Use HTTPS in production. |
| Method | Yes | `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, or `OPTIONS`. |
| Body | For body methods | JSON object or array for `POST`, `PUT`, and `PATCH`. |
| Headers | No | Static request headers represented as key/value pairs. |

The Platform API also supports searchable `metadata`, static-egress `proxy`, `maskDetails`, and controlled creator/system attribution.

```json
{
  "customId": "f395a713-0948-4d60-926e-25d3cd09ec88",
  "saveDetails": true,
  "maxRetries": 4,
  "proxy": true,
  "metadata": {
    "integration": "warehouse",
    "operationId": "op_018f"
  },
  "maskDetails": ["headers.authorization"],
  "request": {
    "url": "https://partner.example.com/v1/orders",
    "method": "POST",
    "headers": {
      "content-type": "application/json"
    },
    "body": {
      "orderId": "ord_8d31",
      "status": "READY"
    }
  }
}
```

The webhook request field is `maxRetries`; `maxAttempts` is rejected. An instance retry policy can impose a lower cap. Job and Agent retry policies keep their separate `maxAttempts` contract.

## Credentials and sensitive details

Static headers are persisted configuration. Do not place a long-lived API key in a screenshot, example, searchable metadata, or unmasked history.

For stronger credential control, call the external API from a Component with `api.httpCall()` and resolve the credential from [Secrets](/operate/secrets). This also lets you compute signatures, rotate versions, validate responses, and write a business transaction around the call.

If a Webhook must contain a sensitive header, disable unnecessary detail retention and configure `maskDetails` for the persisted projection.

## Attempt lifecycle

The Webhooks grid is operational history. A row records status, attempt count, scheduled time, elapsed time, payload size, creator, and metadata. **Message**, immediately after Size, previews the persisted request when it is at most 32 KiB; larger requests show a compact placeholder and remain available from Webhook details. You can still filter by fields in the complete stored request. The outbound request belongs to this one Webhook; delivery attempts are separate evidence, not copies of the request payload.

Open **Delivery attempts** in the Webhook details to inspect each attempt's scheduled, started, response, and retry timestamps, result, and duration. Entries are paginated. The API equivalent is `GET /api/v1/automation/webhook/{webhookId}/attempts?offset=0&limit=20`; it returns `{ data, total, offset, limit }` and accepts a maximum limit of 200.

A delayed Webhook starts `SCHEDULED`; an immediately eligible one starts `PENDING`. `PROCESSING` means delivery is in progress. `FINISHED`, `ERROR`, and `CANCELLED` describe its terminal outcome. `scheduledFor` retains the initial requested time, while `nextEligibleAt` can change for retry backoff.

Attempt evidence can arrive out of order. A late response for attempt 2 does not replace a newer attempt 3 in the summary, and duplicate evidence does not increment the record version. A terminal outcome is not reopened by a late delivery notification. Check individual attempts when investigating timestamps rather than assuming their arrival order is execution order.

A timeout can occur after the receiver accepts the request. The history shows the delivery outcome RevoEngine observed. Check the receiver before retrying an uncertain business effect.

Cancellation stops eligible future processing; it cannot recall a request already accepted by the remote server. Delete and restore change platform visibility, not remote state.

## Design for reliable delivery

A transport timeout is ambiguous: the receiver may have committed the request even though RevoEngine did not receive its response. Put a stable business key explicitly in the receiver-supported request header or body, and require the receiver to enforce it. Neither `customId` nor Webhook metadata automatically implements that receiver contract.

For example, if the partner supports `Idempotency-Key`, configure `request.headers["Idempotency-Key"]` as `order-1:ready:v1` on every attempt for that operation. A newly created Webhook can still represent the same business operation.

`customId` must be a UUID. Reusing an existing value rejects creation; it is not a successful idempotent acknowledgement. After an uncertain create response, inspect that Webhook ID before deciding whether to create another request.

A successful HTTP 2xx finishes delivery. If the partner responds 202 and processes work later, observe its separate business status. Cancellation, `maxRetries: 0` and exhausted retries cannot prove that the receiver made no change. See [delivery guarantees](/patterns/delivery-guarantees).

Use [metadata](/patterns/metadata-and-correlation) to correlate the webhook with the originating Job, Event history, or business object. Alert on terminal failure and exhausted attempts rather than every transient retry.

## Production checklist

- Require HTTPS.
- Use an idempotency key understood by the receiver.
- Set an explicit maximum attempt policy.
- Mask or avoid credentials in retained request details.
- Use static egress only when the receiver needs allowlisting.
- Correlate the row with an operation or business ID.
- Monitor terminal failure and cancellation.

See [HTTP integrations](/low-code/http) when the integration needs an immediate response, multipart data, SSE, or streamed files.

Follow the complete [Event → Job → Webhook example](/patterns/event-to-webhook) to connect configuration, inputs, correlation and observable outcomes.
