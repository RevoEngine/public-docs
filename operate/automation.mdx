Use Automation when work needs a durable outcome that can be inspected after the request that started it. A Job template stores the execution policy. A Job records one execution under that policy.

<span id="job-failure-notifications" aria-hidden="true"></span>

## Choose the right primitive

| I need to… | Configure | Verify the result in |
| --- | --- | --- |
| Run a Component in the background | [Job template](/operate/jobs) | Job History |
| Run work at a recurring time | [Schedule](/operate/schedules) | Schedule History and the target's result |
| React to a business or platform change | [Event](/operate/events) with an optional message filter | Event History and each matching target |
| Deliver a request to an external system | [Outbound Webhook](/operate/webhooks) | Delivery attempts and the receiver's outcome |

For an alert when a Job fails, configure [Job failure notifications](/operate/job-notifications).

## Job lifecycle

```text
SCHEDULED -> PENDING -> PROCESSING -> FINISHED
                         |          ERROR -> retry child
                         +--------> CANCELLED
                         +--------> EXPIRED
```

Open **Jobs → Job History** to inspect status, origin, input/output visibility, Component version, processing time, logs, and retry lineage.

Immediate Jobs start at `PENDING`; delayed Jobs start at `SCHEDULED`. `scheduledFor` records the accepted dispatch time, not an execution-duration limit. Wait reasons distinguish the scheduled time, dispatch, concurrency, and retry backoff. A due Job can remain pending while another execution holds its concurrency slot. Reading a due Job as `PENDING` does not itself change its record version.

Operator actions have deliberately different meaning:

- **Retry** creates another attempt from a failed job.
- **Run now** asks a still-pending job to dispatch immediately.
- **Cancel** requests cancellation for active selections.
- **Delete / restore** changes history visibility without pretending the execution did not happen.

Each record answers a different question. Event History can show that a target was selected while Job History still shows it waiting. A successful Job may have created a Webhook whose delivery is still pending. Follow [one Event through a Job to a Webhook](/patterns/event-to-webhook) to see what to inspect at each handoff.

## Before enabling automation

- Use a dedicated service account as the execution principal.
- Pin a Component version for controlled releases.
- Put stable values in template input and per-run values in job input.
- Set explicit timeout, memory, concurrency, and retry policies.
- Use IANA timezones and test daylight-saving transitions.
- Filter events before scheduling expensive work.
- Make replay and retry safe with idempotency keys.
- Mask or suppress sensitive request and response history.
- Monitor terminal state and retry lineage, not only dispatch acceptance.
