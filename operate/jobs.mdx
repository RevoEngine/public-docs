A Job is a durable execution record for a Component. Use one when a task must outlive an HTTP request, needs a schedule/event trigger, can take meaningful time, or must leave a reviewable status, logs, retry lineage, and result.

## Why use a Job instead of an Endpoint

| Work | Good starting point | Confirm completion with |
| --- | --- | --- |
| Look up one order while the caller waits | [HTTP Endpoint](/operate/endpoint-http) | Its response |
| Export a report for later download | [Job started from an Endpoint returning `202`](/examples/endpoint-job) | Job result and finalized Storage entry |
| Process an uploaded file | [Event](/operate/events) targeting a Job template | Event History and Job result |
| Synchronize with an ERP overnight | [Schedule](/operate/schedules) targeting a Job template | Schedule History and Job result |

A template defines the Component, inputs and execution policy. Job History records the run, including who initiated it, the executor and any retry attempts.

## Find Jobs by trigger and requester

Job History separates the source of a run from the account that initiated it:

| Filter | What it selects |
| --- | --- |
| Trigger Type | Event, Schedule, Request, Execution, or Retry. |
| Trigger | Specific Event or Schedule definitions, searched together by name. |
| Requested by | The account that initiated the run, independently of its execution account. |

The Trigger picker opens with 20 definitions and loads more as you scroll. Search matches a name fragment. Each choice includes its source type; an Event and a Schedule with the same name remain independent selections. You can select both. Choices come from the definitions catalog, so they can appear even when they have no Jobs in the selected date range. Inactive definitions remain searchable; deleted definitions appear when deleted resources are included.

Request, Execution, and Retry rows have an empty Trigger cell. Use Trigger Type to find those runs and Requested by to narrow them to an initiating account. Open the Job details to inspect its execution or retry provenance. For example, select Request and an operator account to find that operator's direct requests without confusing the operator with a Service Account that executed the work. A mixed Batch or Debounce Job has no single initiating user; inspect its Triggers section for each entry's initiator and origin.

## The limit model

The configured timeout is a hard part of the Job contract. It is checked when the template is created or updated and enforced at execution time.

See [Limits and quotas](/platform/limits-and-quotas) for the distinction between platform ceilings, per-instance policy, form validation, and runtime enforcement.

| Limit | Current contract |
| --- | --- |
| Minimum timeout | `1` second. |
| Default timeout | `300` seconds (5 minutes) when a template does not set one. |
| Maximum timeout | Instance quota `jobTimeout`, configurable up to `3540` seconds — **59 minutes**. A lower tenant quota takes precedence, so operators should confirm the current instance value before depending on the maximum. |
| Default memory | `256` MiB when omitted by the Job service. |
| Maximum memory | The low-code runtime ceiling is `2048` MiB — **2 GiB**. This is not an independently configurable `jobMemory` instance quota. Reserve only what the Component needs. |
| Concurrency limit | Per logical key: `1`–`1000` concurrent executions. Lease TTL: `1`–`86400` seconds. |
| Retry attempts | The configured total includes the initial attempt; retries apply after terminal `ERROR`, not cancellation or success. |
| Retry backoff | `maxBackoffSeconds` accepts `60`–`2592000` seconds (up to **30 days**). Jitter never extends the actual delay beyond 30 days. |

The 59-minute limit is intentionally not a substitute for an unbounded worker. Split a longer workflow into idempotent stages, persist the handoff state, and schedule or trigger the next Job. That produces recoverable boundaries and avoids tying one execution to a long-held resource or credential.

## Configure a template

The **Jobs** workspace shows template identity, Component, metadata, actor timestamps, and version. Select a template to open its Details panel: the panel separates **Runtime input**, **Concurrency**, **Retry**, and metadata, and offers **Run** for a deliberate operator invocation. This separation is useful: it makes the settings that change capacity and duplicate-side-effect risk visible before a run is created.

1. Create and activate the Component. In **Jobs**, create a Job template and select the Component and version binding.
2. Choose the execution account and set Runtime input, timeout, memory, concurrency, retry and history visibility.
3. Save the template. Test with [a matching Event](/examples/event-job) and follow the exact Job to its result, or select **Run** on the template for a direct invocation with its required inputs.

```json
{
  "name": "Nightly CRM synchronization",
  "category": "Integrations",
  "componentId": "4d3390ac-2c06-4eb0-8cd4-0b69c3aa531a",
  "executionPolicy": {
    "mode": "SERVICE_ACCOUNT",
    "serviceAccountUserId": "a6e96a8a-0f13-4865-bb07-64260c3de208"
  },
  "timeout": 1800,
  "options": {
    "input": { "region": "eu", "mode": "incremental" },
    "hideRequest": true,
    "memory": 512,
    "concurrency": { "key": "crm-sync-eu", "limit": 1, "retryDelaySeconds": 30 },
    "retry": {
      "enabled": true,
      "maxAttempts": 4,
      "minBackoffSeconds": 30,
      "maxBackoffSeconds": 900,
      "maxDoublings": 4,
      "bypassConcurrencyOnRetry": false
    }
  }
}
```

A new Job Template follows the latest active Component revision when no digest is selected. For a controlled release, select a verified Component content digest from revision history and set `componentDigest` in the template. The digest stays meaningful across instances with different local version numbers. When repairing the Component, preserve the Template's current binding unless the operator explicitly approves a migration.

## Runtime input and trigger provenance

<span id="runtime-input-from-events-and-schedules" aria-hidden="true"></span>

The Job Template’s **Runtime input** is stored as `options.input` and exposed as `api.input().templateInputs`. A [Job-targeting Event](/operate/event-inputs#configure-runtime-input-for-a-job-target) or [Schedule](/operate/schedule-inputs#configure-runtime-input-for-a-job-target) supplies its own Runtime input as `input` on each trigger. In native low-code, use `api.walkTriggers()` to read full entries in order for single Events, grouped Events and Schedules.

Check `triggerType` before reading an entry. New retained triggers also carry `initiatedByUserId` and `origin`, independently of the shared Job executor. The origin keeps the original execution and Assistant conversation references when available. Older Event history may have no initiating account recorded. These audit fields are assigned by the platform; caller-supplied values cannot replace them.

| Trigger | When it appears | Source input |
| --- | --- | --- |
| `EVENT` | Single, Batch, or Debounce delivery | The subscription's Runtime input and the occurrence's own message, type, and metadata. |
| `SCHEDULE` | A cron occurrence or **Run** on the Schedule | The Schedule's Runtime input, metadata, and occurrence identity. |
| `REQUEST` | A manual Job run from the UI or Platform API | The supplied run input and request ID when available. |
| `EXECUTION` | A Job started from another execution, such as by `api.triggerJob` | The supplied run input and source execution ID when available. |

A manual Run can span several Jobs when its trigger array reaches the template’s hard batch limit. The Platform API response keeps `jobId` as the first affected Job and includes every affected ID in ordered `jobIds`. All parts commit together; inspect each Job’s Triggers section to see its assigned entries.

## Trigger a Job from code

Pass the trigger envelope as the second argument to `api.triggerJob`. Put `scheduleFor` in the third argument to run later.

```js
const jobId = await api.triggerJob('Export', {
  input: { orderId: 'order-1' },
  type: 'EXPORT_REQUESTED',
  message: { format: 'xlsx' },
  metadata: { source: 'export-form' },
}, { scheduleFor: Date.now() + 300_000 });
```

Select **Run** to edit **Template inputs** and **Triggers** separately. Template inputs overlay saved defaults for this run; triggers are an ordered array of explicit request envelopes. The Platform API accepts `inputs` and `triggers` together in `POST /api/v1/automation/template/{jobTemplateId}/run`. `trigger` is shorthand for one entry; use either `trigger` or `triggers`. Add `scheduleFor` to run later. Explicit triggers have a 1 MB serialized limit and no separate item-count limit. The platform assigns REQUEST provenance; an application `type` does not turn a request into a retained Event.

Small trigger sets resolve before execution with `deferred: false`. Larger sets expose ordered references with `deferred: true`. Use `api.walkTriggers()` for complete entries in either case. Payloads are retained once rather than duplicated into each stored Job input.

Read the supplied fields from the resulting `REQUEST` or `EXECUTION` entry. `type` is an application label and `triggerType` identifies the source. `message` accepts a JSON value. `metadata` is a JSON object with up to 64 keys and 16 KiB. Keys beginning with `__` are reserved.

In 1.9.0, update existing native low-code and SDK 4.1.0 calls that passed run values directly as the second argument. For example, change `api.triggerJob('Export', { orderId })` to `api.triggerJob('Export', { input: { orderId } })`. Update the Job Component to read the `EXECUTION` trigger's `input` and use `trigger.message` for a separate application message. Keep reading old values from `templateInputs` while Jobs admitted before the upgrade can still run or retry.

SDK 4.1.0 deliberately adopts this new envelope contract. Review callers before upgrading the SDK package; published SDK 4.0.0 keeps its original wire contract.

The separate REST `inputs` field and the Job Template branch of `api.triggerTarget` still apply a shallow overlay. Already published hosted SDK revisions retain their original calling contract.

## Produce an atomic Job batch

Native low-code and SDK 4.1.0 can admit several direct Jobs together:

```js
const jobIds = await api.triggerJobs([
  { name: 'Export', trigger: { input: { orderId: 'order-1' } } },
  { name: 'Export', trigger: { input: { orderId: 'order-2' } } },
], { idempotencyKey: 'orders-export:page-1' });
```

Use 1–100 items and at most 5 MiB of UTF-8 JSON for the complete batch. Acceptance is atomic and returns Job IDs in input order. Each item uses the template's normal executor, concurrency, retry and timeout settings. With Single mode, each item creates a separate Job. A template configured for Batch or Debounce can collect several items into the same Job; the returned IDs remain ordered and can repeat. Configure this in **Jobs → Templates → Execution mode**. All source types participate, including Events, Schedules, manual Run and low-code/REST.

Preparation also has a 64 MiB per-batch ceiling including materialized template inputs. Prepared Job bytes count toward the same cumulative 64 MiB host producer budget for both single and bulk admission. Reduce work per execution when saved defaults are large; a failed preparation accepts no partial Jobs.

The Platform API accepts `{ items, idempotencyKey }` at `POST /api/v1/automation/templates/run`. Reusing a key with the same ordered payload returns the first accepted Job IDs for that authenticated producer on the instance, across requests or executions. Changing the payload under the same key returns a conflict. The first acceptance retains its provenance. Choose a new key for intentional new work, and preserve page keys when reconciling an uncertain response.

Receipts survive Job-history cleanup. Retrying an old key can therefore return IDs whose history has expired; it does not recreate those Jobs. Use a new key only for an intentional new operation.

This API commits Job admission in its own transaction. It does not join `api.transactionDatabase` or `tx.*`; calling it inside a database transaction callback does not make a later database rollback cancel accepted Jobs.

For more work, send bounded pages and await each admission. Ordinary SDK request batching is separate: it groups transport calls and is not a transaction. A successful receipt means accepted, not completed; follow the returned Job IDs.

### Producer budgets

Within one host execution or request, the covered producers allow four active calls, 64 retained calls and 8 MiB retained logical input. Their cumulative budget is 1,000 publication units, 64 MiB logical input and 1,000 attempts. A direct Job batch counts each item as a publication unit. Await pending calls to free retained capacity; cumulative capacity requires a separately admitted execution.

These guards cover direct Job admission, Event publication and REST replay, Webhook publication and manual single retry. They add no new class of AI, Database or Storage limits. The asynchronous selector-based bulk-retry operation retains its own durable workset and bounded worker, including larger selections. Each separate SDK RPC request has its own host producer budget, even when requests carry the same hosted execution ID. Local child work shares its host budget. Delegated remote requests do not share an in-memory parent budget; these limits are not a new global cross-request or instance quota. Event subscriptions can still fan out asynchronously, so observe queue depth, execution concurrency and retained database history.

## Inspect a Job's triggers

Open **Triggers** in Job details. The server-side table pages through source metadata in input order without loading every message. Select a row to load its payload in the read-only JSON editor. Source and definition links open the matching Event, Schedule or originating execution when available. Request and Execution entries use the same view.

Vault-protected input stays masked, including selected-payload reads. Unavailable retained data produces an explicit loading error. Historical payloads above the inspection limit use a bounded preview; this does not change execution or walker input.

Use the [Single, Batch, and Debounce simulations](/patterns/event-job-delivery#explore-the-behavior) to inspect the input of Jobs created by Event subscriptions.

## Limit concurrent Jobs per key

Open **Concurrency** on the Job Template and set **Dynamic key path** to a JSON Pointer such as `/message/priceListId` for Event messages or `/templateInputs/priceListId` for template values. With a limit of 1, Jobs for the same value wait for a slot. Jobs for other values can run in parallel. The limit applies to whole Job executions.

Select **Browse history** to open the Job history for this template. Filter the grid and select a row to inspect its payload. For grouped Jobs, switch between triggers in the preview. Pick a scalar field such as `message.pricelists[0]` to set the JSON Pointer `/message/pricelists/0` in the form. The dialog stays open while you compare runs.

In the Platform API, use `options.concurrency.keyPath`. An optional `options.concurrency.key` shares the namespace with other templates that use the same key. Leaving it blank scopes dynamic slots to this template. A static key without a path works as before. Missing values, objects, arrays, and mixed values in a group use one fallback slot for the configured concurrency limit.

For a grouped Event, an Event field such as `/message/priceListId` must resolve to the same scalar for every trigger to use that value's slot. Configure the Job Template's dynamic key to select the same field. Single Events and homogeneous groups can then share a slot. Use `/input/priceListId` if both Event and Schedule Jobs set that value in their own Runtime input and should share a slot. A retry uses the same saved inputs.

## Choose and retain the executor

`executionPolicy` selects who executes the Job. A direct Platform API or MCP invocation requires the caller's automation permissions. Triggering a Job inside an Endpoint checks the Endpoint's execution account for those permissions.

For **Single** execution, the following policies apply:

| Mode | Executor |
| --- | --- |
| `INHERIT` or an omitted policy | Uses the instance Job default. Existing per-template `triggerUser` bindings retain precedence; when no instance Job policy exists, the established instance Job executor is used, with System as its fallback. |
| `CALLER` | Uses the account initiating the Job. A direct authenticated invocation uses that caller; a Job triggered inside an Endpoint uses the Endpoint's execution account. Unattended triggers without a known initiator cannot use this mode. |
| `SERVICE_ACCOUNT` | Uses the selected active Service Account, which must have platform access and the required roles and resource ACLs. |

For **Batch** and **Debounce**, the template's configured `triggerUser` or Service Account executes the whole Job. Otherwise the Job inherits an instance Jobs Service Account, then falls back to the established instance Job account or System. `CALLER` does not reject authorized admissions or select the first caller as the batch executor. The initiating account and Assistant conversation do not split collection. Grouping mode comes from the Job Template's `delivery` configuration.

Use a dedicated Service Account for unattended work. A selected Service Account and `triggerUser` must name the same account. For Single, `CALLER` also requires clearing `triggerUser`; Batch and Debounce retain that binding as their shared executor when present. Clear the legacy alias with `null` when replacing it. The Endpoint compatibility migration preserves existing instance Job defaults and template bindings.

Jobs capture their executor when the durable record is created. A mixed Batch or Debounce Job has an independent Job origin and no single job-level initiator; each trigger keeps its own `initiatedByUserId` and `origin`. `api.currentUser()` returns that executor; Jobs do not have the Endpoint's separate business-identity setting. History distinguishes `executionUserId` from `initiatedByUserId`. A retry keeps the original executor and initiator even if a Template or instance default changes, and rechecks the executor's availability and current permissions before running.

For example, a human user invokes an Endpoint executing as System with Caller business identity. If that Endpoint triggers a Single `CALLER` Job, the Job executes as System, `api.currentUser()` in the Job is System, and `initiatedByUserId` remains the original human user. A Template selecting a different Service Account uses that account instead.

The Job executor's roles authorize operation families, while resource ACLs determine access to particular Databases, Storage objects, and other restricted targets. Configured administrator Service Account execution also requires approved Component and library code. An approval failure produces a terminal error rather than repeatedly retrying unapproved code; inspect the failure and approve the intended executable version before starting new work.

The platform rejects retry backoff above 30 days before queueing. If an absolute requested run time becomes due while the request is being processed, the Job is dispatched immediately; the queue is never given a timestamp in the past.

## What a Job gives you

```text
template / schedule / event / explicit run
  -> durable Job record
  -> authorization and current-definition resolution
  -> one claimed execution attempt
  -> logs, result, status, and retry lineage
  -> terminal state and operator-visible evidence
```

The durable record makes these questions answerable after the caller has gone away:

- Did the work start, remain pending, get cancelled, expire, finish, or error?
- Which component version and execution principal were selected?
- Which input/result fields were intentionally hidden from history?
- Was this a retry child, and what happened on the preceding attempt?
- Did a downstream artifact exist and finalize successfully?

## Design for retries and timeouts

A Job can produce an external effect before its outcome is confirmed. Application retries or a deliberate new run can repeat that effect. A timeout, worker interruption or failed response does not prove that the remote service made no change; retry policy is not a guarantee of successful delivery or exactly-once effects.

1. Create an idempotency key per business effect before calling the provider.
2. Store/check the provider correlation ID before scheduling a retry.
3. Make each stage independently safe to run again.
4. Keep remote calls, large file work, and database writes bounded.
5. Use a concurrency key for a shared account, file, or customer when two writes would conflict.
6. Break work approaching the timeout into resumable chunks; write a checkpoint to a Table or Storage before enqueueing the next chunk.

<Warning>
Do not increase timeout, memory, or retry count merely to hide a failing workflow. Use the Job's logs, trace, selected version, and retry lineage to establish the failed boundary first.
</Warning>

## Operate a Job

Use **Jobs → Job History** to inspect an exact Job ID, its status, current/selected version, logs, timing, and retry root. “Accepted” means the request created or scheduled durable work; it is not a success result. Confirm `FINISHED` or a finalized artifact before notifying users or triggering a dependent business process.

The **Trigger** reference identifies the Event or Schedule definition that started the Job; the history reference identifies its particular occurrence. For Event Jobs, the definition is resolved from the receipt for that exact Job execution, so two Events targeting the same template remain distinguishable. The list exposes this reference as `triggerId` and its display name as `triggerName`. A missing retained definition is shown as unavailable rather than inferred from the template.

For a bulk action, review the selected or filtered scope and eligible count before confirmation. After acceptance, **View progress** opens the background operation. Review processed, skipped and failed counts: a finished operation can include individual failures. Closing its progress view does not cancel accepted work.

## Read attempt status and Job result

Job History separates the status of one attempt from the result of its full retry history:

| Column | Meaning |
| --- | --- |
| **Attempt status** | The selected attempt's own status. An earlier `ERROR` remains an error even when a later attempt succeeds. |
| **Attempts** | That row's attempt number and automatic retry limit, such as **Attempt 2 of 3** or **Attempt 2 of ∞**. Without automatic retry, it starts at **Attempt 1 of 1**. |
| **Job result** | The current result across the history, including manual retries. |

Outcome summaries cover attempts created after the 1.6.6 cutover. Existing Job rows remain available, but the upgrade does not rebuild their history; their aggregate result can be empty. A new retry of an older Job summarizes the new attempts only. Work already running during the upgrade can finish normally.

Filter **Job result** to distinguish **Failed** from **Succeeded after retry**.
**Retry pending** includes an accepted retry waiting to start; it does not mean the
history has reached a final failure. **In progress**, **Succeeded**, **Cancelled**
and **Expired** describe the other outcomes. These filters apply to the complete
query before pagination, rather than only the rows already loaded.

For example, an earlier row can show **Attempt status: ERROR** and **Job result:
Succeeded after retry**. Manual retry starts a new run at attempt 1 with a fresh
automatic retry budget, while its outcome remains part of the same Job history.
The attempt number displayed on an older row does not become the latest attempt's
number. Once no attempt is running or scheduled and no automatic retry is pending,
**Retry** on an earlier failed or cancelled row starts another manual run. Repeated
clicks while its child is still live reuse that child. Bulk-operation replays retain
their original result ID, even when that attempt has already finished.

## Cancellation and recovery

Cancelling a pending Job prevents execution. Cancelling a running Job records a durable
request; its status remains `PROCESSING` until the worker acknowledges that request or
recovery confirms that its execution lease expired. The details panel shows cancellation
as pending during that interval. A cancellation request cannot undo an external action
that already completed.

Accepted Jobs retain their payload, delivery intent and retry lineage independently of
transient cache availability. Delivery retries do not create another business attempt.
Committed delivery and retry intents are recovered every minute after temporary
queue failures. These transport retries keep the accepted Job identity. Auxiliary
notification scheduling uses a short wait, so an unavailable queue does not keep
a completed Job holding its execution capacity. Fresh matching heartbeats protect
an active Job during recovery, including a heartbeat arriving while it is read.

A lost worker with an unknown effect is reported as requiring recovery; inspect the
original target before explicitly retrying a write. Automatic retry settings remain
separate from infrastructure delivery and do not guarantee exactly-once external effects.


## Follow-up execution through Events

Ordinary Component Jobs publish native success, failed-attempt and final-failure signals. Use `JOB_EXECUTION_SUCCEEDED` to chain a follow-up Job, `JOB_ATTEMPT_FAILED` to react to each failed attempt, or `JOB_EXECUTION_FAILED` to act only when no automatic retry remains. Filter by the source Job template and make the follow-up action idempotent. See [Job execution Events](/operate/event-types#chain-component-jobs-from-execution-outcomes) for the payload, execution-series identity and cycle protection.

See [Job concurrency](/patterns/job-concurrency) for key and slot semantics, and [retry policy](/patterns/retry-and-uncertainty) for attempt limits and backoff.

For Event dispatch, Webhook attempts and business-effect guarantees, compare [delivery boundaries](/patterns/delivery-guarantees).
