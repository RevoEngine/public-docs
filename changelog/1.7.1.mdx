RevoEngine 1.7.1 retires the legacy Files resource and deprecated low-code entrypoints. Storage remains the file lifecycle for uploads, generated artifacts and transfers. SDK 3.0.0 exposes the same current runtime contract, including canonical account metadata fields.

## Highlights

- Removed the legacy Files workspace, Platform API endpoints and resource discovery.
- Removed deprecated low-code methods and the `libs` alias; use the current runtime namespaces and `lib`.
- Standardized account responses and inputs on `metadata` and `metadataAdvanced`.
- Updated Monaco declarations and SDK 3.0.0 to the current supported authoring contract.
- Preserved Storage uploads, attachments and the shared upload flows used by account images.
- Hardened account labels, avatars, editor documentation and chat diagrams against injected content.
- Removed spurious error diagnostics for expected `util.sleep` cancellation while preserving cancellation and timeouts.
- Made concurrent requests wait for ordinary instance readiness instead of reporting schema-migration maintenance.

## In detail

## Storage throughout the application

The legacy Files resource is retired from navigation, dashboards, search and the Platform API. Use Storage entries and their `storageEntryId` for file operations. Existing Storage upload sessions, HTTP transfers, SFTP transfers and chat attachments continue through their existing lifecycle.

Removing Files does not turn an old file identifier into a Storage entry. Applications must use the Storage contract when selecting an upload destination, opening an artifact or returning a download to a client. Storage authorization, finalization and retention continue to apply.

Read [Storage](/operate/storage) and [Storage uploads](/operate/storage-uploads).

## Current low-code namespaces and SDK 3.0.0

Application code now uses the supported `api`, `storage`, `util`, `transport`, `vault`, `agent` and `lib` surfaces. Deprecated method aliases are removed from execution and editor completion. Shared implementations used by the current namespaces remain available through those namespaces.

SDK 3.0.0 is a breaking authoring-contract update. Replace deprecated method calls and `libs` references before upgrading, then check the generated declarations for the supported signatures. SDK and platform versions are independent; new hosted Components use the platform's SDK pin.

Read the [low-code reference](/low-code/reference/index) and [Node.js SDK](/developers/sdk-overview).

## Canonical account metadata

`api.currentUser()`, account responses and account requests use `metadata` and `metadataAdvanced`. The retired field names are removed from declarations and are rejected in account writes and query selectors. The same contract is available in Monaco and SDK 3.0.0.

Applications that expose their own established user-response format can map these canonical fields in application code. Such a mapping belongs to that application's response contract; it does not restore removed fields on `LoggedUser` or the Platform API.

Read [Users](/operate/users).

## Safer identities, editor content and diagrams

Account names, email addresses and identity-provider details render as literal text in labels and grids. Avatar addresses and labels remain contained within image attributes; unsafe addresses use the existing initials or missing-image fallback. Profile image uploads continue through Storage.

Editor documentation and chat diagrams have stronger protection against injected markup and styles. Code editing, useful diagram labels and mathematical expressions retain their existing authoring workflow.

Read [Users](/operate/users) and [Studio sessions](/build/studio-sessions).

## Sleep follows the execution lifecycle

`await util.sleep(ms)` pauses within the current execution's timeout budget. Cancellation or expiry still interrupts the wait, and finishing an execution clears pending waits. An interrupted wait continues to reject rather than completing successfully.

Expected wait cancellation no longer produces a spurious error diagnostic. Real timer failures and errors from other platform calls retain their normal diagnostics. Await delays that the workflow needs before returning its result.

Read [Low-code overview](/low-code/overview) and [Jobs](/operate/jobs).

## Requests wait for instance readiness

Concurrent requests now wait while an instance prepares its data connection, checks its schema and initializes required system schedules. Ordinary preparation no longer returns a schema-migration maintenance response solely because another request is preparing the instance.

Maintenance protection remains in place when a schema migration is actually in progress. Connection and system-schedule initialization failures retain their normal failure handling; requests use the instance only after the required preparation succeeds.

Read [Databases](/operate/databases#instance-readiness).
