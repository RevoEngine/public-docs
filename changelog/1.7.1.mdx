RevoEngine 1.7.1 adds conditional Database upserts for repeatable imports, completes the move from legacy Files to Storage and removes deprecated low-code APIs. Review the compatibility changes below before upgrading applications or adopting SDK 3.0.0.

## Highlights

- Synchronize repeated data with optional change detection and filters on existing Database rows.
- Preview Database read plans with `debug: true` without fetching records.
- Retired legacy Files; use Storage for uploads, downloads and generated files.
- Removed deprecated low-code methods and the `libs` alias; SDK 3.0.0 uses the current runtime API.
- Standardized account fields on `metadata` and `metadataAdvanced`.
- Improved Assistant context continuity, Live Preview recovery and Sandbox debugging.

## In detail

## Conditional Database upserts

The 3 November update to 1.7.1 adds `skipUnchanged` to avoid rewriting identical imported data and `filter` to control updates using current Database values. New rows are inserted independently of the filter. Compare all supplied fields or select an `include` or `exclude` list; changes only outside the compared set are intentionally skipped. Use `affected` to count actual writes in conditional mode and `return: false` when row data is unnecessary. Skipped writes do not create row-audit updates.

Read [Database mutations](/operate/databases#conditional-upserts) and the [low-code API reference](/low-code/reference/api#api-upsertDatabaseData).

## Preview Database read plans

Use `debug: true` on a structured Database read to inspect the complete estimated plan before fetching records. It now returns a diagnostic result only, including an optional count plan. Remove `debug` when the application needs records.

Read [Database read diagnostics](/operate/databases#preview-a-read-plan).

## Legacy Files retired

The legacy Files workspace and its Platform API endpoints are no longer available. Use Storage and `storageEntryId` for file operations. Existing Files identifiers are not Storage entry identifiers; update integrations that still depend on the retired resource.

Read [Storage](/operate/storage) and [Storage uploads](/operate/storage-uploads).

## Deprecated low-code APIs removed

Replace deprecated method calls with their current equivalents and change `libs` references to `lib`. SDK 3.0.0 is a breaking update that follows the same supported runtime API. Check application code against the current reference before upgrading.

Read the [low-code reference](/low-code/reference/index) and [Node.js SDK](/developers/sdk-overview).

## Account metadata fields

Account requests, responses and `api.currentUser()` use `metadata` and `metadataAdvanced`. Update integrations and account query selectors that use retired field names; those names are no longer accepted.

Read [Users](/operate/users).

## Safer identities, editor content and diagrams

Account names, email addresses and identity-provider details render as literal text in labels and grids. Avatar addresses and labels remain contained within image attributes; unsafe addresses use the existing initials or missing-image fallback. Profile image uploads continue through Storage.

Editor documentation and chat diagrams have stronger protection against injected markup and styles. Code editing, useful diagram labels and mathematical expressions retain their existing authoring workflow.

Read [Users](/operate/users) and [Studio sessions](/build/studio-sessions).

## Sleep follows the execution lifecycle

`await util.sleep(ms)` pauses within the current execution's timeout budget. Cancellation or expiry still interrupts the wait, and finishing an execution clears pending waits. An interrupted wait continues to reject rather than completing successfully.

Expected wait cancellation no longer produces a spurious error diagnostic. Real timer failures and errors from other platform calls retain their normal diagnostics. Await delays that the workflow needs before returning its result.

Read [Low-code overview](/low-code/overview) and [Jobs](/operate/jobs).

## Requests wait for instance readiness

Concurrent requests now wait while an instance prepares its data connection, checks its schema and initializes required system schedules. Ordinary preparation no longer returns a schema-migration maintenance response solely because another request is preparing the instance.

Maintenance protection remains in place when a schema migration is actually in progress. Connection and system-schedule initialization failures retain their normal failure handling; requests use the instance only after the required preparation succeeds.

Read [Databases](/operate/databases#instance-readiness).

## Reliable background handoff

Temporary queue-transport failures retry within the platform deadline, including
requests already in flight. Committed upload, indexing and Job-notification work
is recovered every minute, while upload responses and completed Jobs use a short
wait for auxiliary publication. Retry keeps its durable identity and repairs an
unavailable task name without replaying customer Job logic.

Email preparation can recover after an interruption before the delivery provider
is called. An uncertain result after a send still requires review to avoid sending
the same message again. Active Job heartbeats remain protected during recovery.

Read [Jobs](/operate/jobs) and [Storage](/operate/storage).

## Reliability update · 7 November

The Assistant now keeps the context it needs when a long conversation is shortened, including references to earlier tool results. Large reads can be continued in smaller pages. Terminal executions that reconnect stay pending until their original outcome is confirmed.

Live Preview can reconnect to an existing read-only browser session after a brief interruption. For a pending human interaction, use **Finish & resume** once the original tab and your access are confirmed. The compact preview keeps its position while you resize it.

Direct Sandbox debug applies temporary library edits for the current request, including when execution uses a pinned Studio release. Upload policy rejections and webhook delivery failures retain their recorded outcomes and are distinguished from platform failures in operational diagnostics.

Read [Live Preview](/ai/browser#follow-live-preview), [Studio sessions](/build/studio-sessions) and [Webhooks](/operate/webhooks).
