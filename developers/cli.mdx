`@revoengine/cli` is the official command-line client for RevoEngine. It requires Node.js 24 or newer.

```bash
npm install --global @revoengine/cli
```

The package installs `revo` as the primary command. `revoengine` remains a compatible alias.

CLI **1.0.34** introduces property omission across synchronized definitions, strict command validation, atomic workspace state and safer terminal process and file handling. Omitted-mode writes require the target API capability described below.

CLI **1.0.33** introduced durable Database Operation receipts and verified completion for schema writes, current Endpoint SSE configuration validation, and browser recordings at the selected viewport and frame rate. Schema operations and SSE require Platform 1.7.0; native tests require their matching Platform API. Publishing the CLI does not enable these features on an older instance. Ordinary schema writes remain compatible with instances returning a completed Table synchronously.

## Sign in

```bash
revo auth login
revo auth status
```

Login prompts for an API key, validates it through `/api/v1/me`, and infers the instance bound to the key. Remove the stored default login with:

```bash
revo auth logout
```

Interactive credentials live in the operating-system config directory:

- macOS and Linux: `~/.config/revoengine`
- Windows: `%APPDATA%/revoengine`

Named environment profiles are stored separately from the default login. Logout does not delete those profiles.

## Essential commands

To connect a computer or virtual machine for an Assistant, follow [Connect a terminal](/ai/terminals). After signing in with a personal API key, `revo terminal connect --workspace "$HOME/projects/my-project" --name "Work VM"` creates a pending request. Its owner must approve it in **Settings → Vault → Terminals** from a browser session before the Assistant can use it. Later connections with the same profile and terminal name preserve the device registration; an additional directory becomes a separately approved workspace. Approved online workspaces are available directly to the Assistant. See the terminal guide for connection recovery, background services, browser state and file transfers.

```bash
revo --help
revo -i
revo endpoints
revo search CODE customerId
revo search SIMPLE invoice
revo request GET /api/v1/me
revo request POST /api/v1/endpoints '{"name":"Example"}'
```

`revo request` is a low-level escape hatch for authenticated Platform API calls. Prefer dedicated commands when they provide planning, confirmation, local state, or verification.

## Argument and workspace safeguards

CLI 1.0.34 introduces the safeguards below. Unknown options, missing values,
invalid booleans and unsupported combinations stop before authentication or execution.

Boolean options accept a bare flag, `--flag=true`, `--flag=false`, or `--no-flag`.
Explicit values use lowercase `true` or `false`; `0`, `1`, `no`, `FALSE` and empty
values are rejected. Conflicting repeated options are rejected too. For example,
use `--no-force` instead of `--force=no`.

Use `revo plan` for a repository deployment preview, or the corresponding family
`plan` before `push`. Named migration commands accept `--dry-run` to follow their
read-only plan flow, and `env apply` also supports it. Other command families
reject it rather than executing a write under a preview flag.
`revo <command> --help` shows help without connecting or executing. Conflicting
aliases are rejected too. Terminal connection commands do not accept a child
command or hidden options after `--`; raw request JSON and query values remain data.

Workspace-changing commands take an exclusive local project lock. A concurrent
writer fails before changes; finish the active command and retry. Read-only plan
and diff remain available. A lock is recovered only from a confirmed dead owner;
lock age does not evict a live or unverifiable process. Stale baseline snapshots
are rejected, and local JSON state uses atomic replacement so an interrupted
write before replacement retains the previous valid file. These safeguards
complement the target API's version checks; a deployment still consists of
separately verified remote operations. Project init/update adds the transient
`.revoengine/workspace-write.lock/` directory to Git ignores; the existing baseline
file keeps its normal repository policy.

## Native tests

CLI **1.0.31 or newer** provides `revo tests list`, `run`, `resume` and `cancel` for captured fixture suites. Test local Component source without publishing it, or select stored suites with `--remote`. ## Configuration precedence

For the default client, configuration resolves in this order:

1. command flags such as `--url` and `--token`;
2. environment variables;
3. stored interactive configuration;
4. the default API origin.

Named `--from` and `--to` environment profiles resolve independently and are not mixed with the default environment variables.

Supported environment aliases include:

```bash
export REVO_URL="https://api.revoengine.com"
export REVO_TOKEN="$REVO_CI_TOKEN"
revo endpoints
```

`REVO_BASE_URL`, `REVO_API_KEY`, and their `REVOENGINE_*` equivalents are also supported.

<Warning>
  Pass CI credentials from the CI secret store. Do not commit tokens in shell scripts, `.env` files, project metadata, or `.revoengine/`.
</Warning>

## Preserve destination configuration during synchronization

`--omit` lets operators preserve selected destination settings while synchronizing
other definition changes. Push and deploy preserve instance values; pull preserves
existing local values. It applies to Components, Database Tables and Views,
Service Accounts, Agents and Agent Plugins, Job Templates, Endpoints, Schedules,
Events, Groups and Role Groups. CLI 1.0.34 introduces this option.

For example, keep an Endpoint's operator-configured inputs while synchronizing
its other settings:

```bash
revo endpoints plan --all --omit=options.input
revo endpoints push --all --yes --omit=options.input
```

For a repository containing several kinds of definition, qualify each path:

```bash
revo plan --prune --omit=job-template:options.input,endpoint:options.input --out reviewed-plan.json
revo deploy --prune --yes --omit=job-template:options.input,endpoint:options.input --reviewed-plan reviewed-plan.json
```

Use the same policy for planning and deployment. The CLI ignores those paths when
comparing managed changes and retains their current instance values when saving
another field. `--force` still preserves them. New definitions use source values
for initial configuration because no destination value exists yet. Pull supports
both repository and dedicated family commands:

```bash
revo pull databases --omit=name --yes
revo pull --all --omit=name --yes
revo job-templates pull --all --omit=inputs
```

During pull, omitted properties keep their local values, including with `--force`.
Other properties refresh from the instance. A first pull initializes the full source
because no local destination exists. Independent local source proofs let ignored
local edits coexist with managed remote updates; local managed edits retain the
usual conflict protection. No resource metadata setting is required.

A nested path such as `options.input.region` preserves only that key. JSON Pointer
paths, such as `/options/input/customer.region`, address literal dots in a key.
Arrays can be omitted as a whole; indexes and wildcards are rejected. Job Template
`inputs` is a legacy alias of `options.input`. Event `input` and `inputMode`
also cover their legacy `extensions.*` representation, including nested input keys.
Endpoint uses `options.input` and
`options.noResult`. Unknown paths, identity fields, versions, structural changes
and dependency references cannot be omitted. An unqualified path must be supported
by every selected family; qualify paths when the families have different fields.

Existing synchronization baselines are reused only when they can prove the
remaining managed state. Otherwise reconcile a fresh full snapshot or explicitly
review the ordinary overwrite workflow. Removing an omission returns those fields
to CLI management and requires renewed comparison; it never silently approves
instance changes. A saved plan also becomes stale when the instance changes after
review, including changes to omitted values. Complete managed source manifests
are reviewed too, including the initial values used to create new definitions. Regenerate and review the plan before
retrying. Before an omitted-mode mutation, the CLI requires a fresh Platform API `/api/v1/me`
response with `capabilities.atomicResourceUpdates: true`. An older API is rejected
before writing, even with cached authentication. Read-only pull does not require
this write capability. The CLI advertises its own
support through `capabilities.syncOmit` in `revo --version --json`.

If saving another runtime option would normalize an omitted missing or null
property, the CLI stops before writing. Reconcile the target defaults or preserve
the complete options object. A deployment remains a sequence of separately
guarded operations.

## Automation output

Commands that support `--json` emit machine-readable output for CI and review tooling. Human-readable progress and streamed debug logs use stderr where appropriate, leaving the final result on stdout.

The interactive update notifier checks for a newer CLI release at most once every 24 hours. Disable it in CI with `REVO_NO_UPDATE_NOTIFIER=1` or `--no-update-notifier`.

## Submit a long schema change

Normal Table push and full deploy submit durable Database Operations, wait for terminal success, and verify the resulting Table before moving their environment baseline. A failed or unreadable operation prevents later dependent phases from being deployed.

To leave one schema operation running after the command exits:

```bash
revo database-tables push 'Sales/Orders#1234abcd' --yes --async --json
```

The result reports `status: "accepted"` with an `operation` containing `jobId` and its current status. Acceptance is not deployment success. Inspect that ID in Database Operations or with `revo request GET /api/v1/databases/operations/<jobId>`. After `FINISHED`, rerun normal push to verify the portable definition and reconcile the baseline.

For a transport retry across invocations, pass `--idempotency-key <uuid>` with the same target, body and original optimistic version. Admission-only mode requires one explicit Table Stable Key; it cannot prune or use `--all`. Full deploy rejects `--async` because Views, Components and other consumers must wait for schema readiness. Existing reviewed plans and mutation approval requirements continue to apply.
