A CLI project maps RevoEngine component definitions to a local workspace while keeping generated editor types and synchronization state separate from authored files.

## Initialize a workspace

```bash
revo project init ./app \
  --identity-mode stableKey \
  --stable-key-name stableKey \
  --resources component
```

Run `revo project` as the short interactive form, or refresh an existing project with:

```bash
revo project update ./app
```

Initialization writes or refreshes:

```text
.revoengine/
  revo.json
  types/
    revo.editor.d.ts
    revo.editor.definitions.json
```

The command also patches the workspace `tsconfig.json` or `jsconfig.json` and updates root `.gitignore` so generated editor bundles remain local by default. When the RevoEngine code lives in a nested directory, the root `.revoengine/` directory remains the single state location and `revo.json` stores the workspace path.

Component pull/push creates and updates `.revoengine/revo.lock.json` as synchronization state.

## Identity strategy

New projects should use `stableKey`. The configured metadata value identifies the same logical component across instances even though component and element UUIDs differ.

```json
{
  "componentIdentity": {
    "mode": "stableKey",
    "metadataProperty": "stableKey"
  }
}
```

Stable-key mode manages only components that contain the configured metadata property. Missing or duplicate keys block unsafe plan/pull/push operations. Use `componentId` mode only for a workspace intentionally bound to one instance.

Plan and apply missing metadata explicitly:

```bash
revo metadata plan --env default
revo metadata apply --env default --yes
```

## Pull, plan, and push

```bash
# Pull one component or all active components
revo component pull "$COMPONENT_ID"
revo component pull --all --yes

# Review local/remote state without writing
revo component plan --all
revo component plan --all --json
revo component plan --all --strict

# Push selected or all local components
revo component push "$COMPONENT_ID"
revo component push --all --yes
```

Pulled components use a stable tree:

```text
Components/
  Forms/
    Customer_Card-<component-id>/
      component.json
      elements/
        1_template.ts
        2_logic.ts
```

Each component manifest is stored beside one source file per element. Components without a category are placed under `Components/__no_category__/` while the manifest preserves `category: null`.

## Conflict model

`.revoengine/revo.lock.json` records the last successfully pulled or pushed remote baseline. The CLI compares three states before overwriting anything:

1. current local component files;
2. the lock baseline;
3. current remote state.

A clean local copy can fast-forward when only the remote changed. If both sides changed, pull or push reports a conflict instead of choosing a winner. `--force` bypasses lock-content safety for an explicitly selected bulk operation, but it does not bypass missing or duplicate stable identity.

<Warning>
  The lock file is synchronization evidence, not deployed source of truth. RevoEngine remains authoritative for deployed state; local component files are the desired source you are proposing.
</Warning>

## Configure Single, Batch or Debounce Jobs

CLI **2.1.0** synchronizes Job Template execution modes with Platform **1.9.0 or later**. Collection belongs to the Job Template, so matching Event, Schedule, manual and programmatic triggers can join the same Job. See [Job execution modes](/patterns/event-job-delivery) for grouping boundaries and runtime processing.

Pull the current definitions from the selected project before editing their `job-template.json` manifests:

```bash
revo job-templates pull --all
```

Merge one of these fragments into a pulled manifest, keeping its identity, Component binding and other settings:

<CodeGroup>
```json Single
{
  "delivery": null
}
```

```json Batch
{
  "delivery": {
    "mode": "BATCH",
    "maxSize": 100,
    "maxWaitSeconds": 600
  }
}
```

```json Debounce
{
  "delivery": {
    "mode": "DEBOUNCE",
    "maxSize": 100,
    "maxWaitSeconds": 600,
    "quietPeriodSeconds": 30
  }
}
```
</CodeGroup>

`maxSize` accepts 2–1000 triggers. Wait and quiet periods accept 1–3600 seconds. Debounce requires `quietPeriodSeconds` no greater than `maxWaitSeconds`; Batch does not accept a quiet period. Configure dynamic concurrency separately with `options.concurrency.keyPath`, for example `/message/orderId`.

Review the plan before applying it. These commands cover all managed Job Templates in the workspace:

```bash
revo job-templates plan --all
revo job-templates push --all --yes
```

<Warning>
  In a CLI manifest, removing `delivery` or setting it to `null` requests **Single**, including when updating an existing Batch or Debounce Job Template. To preserve the target's execution mode while synchronizing other settings, use `--omit=delivery` on both `plan` and `push`.
</Warning>

Older Event-level `delivery` policies are rejected. Move the policy to the target Job Template and remove the former Event `keyPath`; choose any dynamic concurrency path separately. Event and Schedule `input` is retained on each trigger, while template defaults remain in `templateInputs`. CLI 2.1.0 ignores retired `inputMode` fields and excludes them from fresh pulls and API writes. Re-pull definitions and regenerate reviewed plans after upgrading; follow [Upgrade to 1.9](/developers/upgrading-to-1-9) when updating the Job's Component code.

## Portable owners and execution policies

Use `owner: { "type": "system" }` for a Group or Service Account whose management owner is the built-in System account. An ordinary Service Account owner uses `owner: { "type": "service-account", "stableKey": "operations-worker" }`. The CLI resolves these references in the target instance. A Service Account manifest owner becomes management access; it does not grant execution roles. System itself is protected and is excluded from managed-account exports, updates, and pruning. A target without a valid physical System account is blocked before dependent writes.

Endpoint `execution` identifies the Component. The separate `executionPolicy` chooses permission identity and business `currentUser` behavior:

```json
{
  "executionPolicy": {
    "mode": "SERVICE_ACCOUNT",
    "serviceAccount": { "kind": "system" },
    "currentUser": "CALLER"
  }
}
```

For an ordinary executor, use `serviceAccount: { "kind": "service-account", "stableKey": "operations-worker" }`. Both Endpoints and Job Templates accept `INHERIT`, `CALLER`, or `SERVICE_ACCOUNT`; omit `serviceAccount` for the first two. Only Endpoints have the independent `currentUser` choice. Job code sees the captured executor and records the initiator separately.

Instance execution defaults are target-local settings under **Settings → Endpoints** and are not copied by resource migration. Existing Job `executionPrincipal` manifests remain supported; use either that legacy reference or `executionPolicy`, not both. Writing an explicit policy clears the legacy executor alias. Configured `SERVICE_ACCOUNT` execution with administrator permissions requires approved Component and library code; see [Endpoint configuration](/operate/endpoint-configuration#execution-policy).

## Synchronize Applications and Endpoints

Applications require Platform **1.9.2 or later** and CLI **2.2.0 or later**. Keep their definitions with the Endpoints that use them:

```bash
revo project update ./app --resources application,endpoint,component
revo pull --resources application,endpoint --yes
revo applications plan --all
revo endpoints plan --all
```

An Application manifest uses its immutable URL key as portable identity. For example, `Applications/portal/application.json` can contain:

```json
{
  "kind": "application",
  "key": "portal",
  "name": "Customer portal",
  "description": "Customer-facing HTTP integration",
  "cors": {
    "mode": "allowlist",
    "allowedOrigins": ["https://portal.example.com"]
  }
}
```

In a pulled Endpoint manifest, select that Application without carrying an instance-specific UUID:

```json
{
  "application": { "key": "portal" },
  "route": { "method": "POST", "path": "/orders" }
}
```

This Endpoint fragment supplements the existing manifest; retain its Stable Key, Component binding, options and execution policy. The CLI resolves `portal` to the target instance's Application. Omitting `application` preserves the existing Default behavior; an explicit Default reference is `{ "system": "@default" }`.

Review and apply the whole dependency graph when introducing a new Application and Endpoint together:

```bash
revo plan --out reviewed-plan.json
revo deploy --yes --reviewed-plan reviewed-plan.json
```

Applications are synchronized before dependent Endpoints. Route collisions are checked within an Application. The system Default identity cannot be renamed or deleted; its CORS, invocation and anonymous policies remain editable. Application deletion is also blocked by retained Endpoint assignments, including deleted Endpoints with history. Keep source and target CORS requirements explicit, and use `--omit=application:cors` in a mixed-family command when the destination owns that policy.

### Synchronize typed caller policies

The Platform API uses target-local account IDs. CLI manifests distinguish human users from Service Accounts and resolve Service Accounts by Stable Key:

```json
{
  "invocationPolicy": {
    "mode": "allowlist",
    "users": [{ "instanceId": "11111111-1111-4111-8111-111111111111", "userId": "22222222-2222-4222-8222-222222222222" }],
    "serviceAccounts": [{ "kind": "service-account", "stableKey": "accounts/integration" }],
    "groups": [{ "type": "group", "stableKey": "groups/portal-callers" }]
  },
  "anonymousAccess": { "enabled": false, "requestsPerMinute": 30, "maxConcurrent": 2 }
}
```

Choose `all`, `allowlist` or `denylist`; `all` requires empty lists. A direct member or verified Group membership matches an allowlist; either match blocks a denylist. Groups resolve by Stable Key to live target Group identities, with source/target revision fences. Omitted `groups` preserves the target list when updating a policy; explicit `groups: []` clears it. Existing invocation roles still apply. Same-instance users require a current typed account readback. Crossing instances requires an explicit environment mapping in local `.revoengine/revo.json`; users are never matched by email:

```json
{
  "applicationUserMappings": {
    "production": [{
      "sourceInstanceId": "11111111-1111-4111-8111-111111111111",
      "sourceUserId": "22222222-2222-4222-8222-222222222222",
      "targetUserId": "33333333-3333-4333-8333-333333333333"
    }]
  }
}
```

Missing or ambiguous mappings block the plan. Saved plans fence these mappings, target policies and account identities/revisions. Omitting `invocationPolicy` or `anonymousAccess` preserves the target; explicit `null` resets the policy. Use `--omit=application:invocationPolicy` or `--omit=application:anonymousAccess` to preserve each complete target policy. Retained caller and Group references block unsafe Service Account or Group pruning.

An Endpoint opts in separately with top-level `allowUnauthenticated: true` and an explicit dedicated Service Account execution policy. Both Application and Endpoint gates must permit anonymous execution. Published named Application calls use the configured hostname and keep the path unchanged; `/services/...` has no special routing meaning. Local preview rejects unsupported caller policies, anonymous admission and explicit wire formats; use the actual Endpoint runtime for those checks.

Native file modes use `options.requestBody: {"mode":"storage"}` or `options.responseBody: {"mode":"storage"}`. The Component selects an exact upload-session or file directive; no folder is configured inside `requestBody`. CLI 2.2.0 checks a fresh `endpointStorageTransports: true` capability for every managed native plan (including unchanged and omitted-retained options) and before native configuration writes. Missing capability blocks these modes without changing old inline formats. Local preview rejects native modes. Published preview rejects known native catalog routes before reading bytes; Default callers denied catalog access retain legacy 2 MiB request forwarding with an unknown-format warning. Use the real Endpoint runtime for streaming checks.

See [Applications and CORS](/operate/endpoint-applications) for runtime addresses and [request and response formats](/operate/endpoint-bodies) for wire contracts.

## Debug local source

```bash
revo component debug "$COMPONENT_ID" \
  --body '{"customerId":"customer-1"}' \
  --timeout 30 \
  --memory 256 \
  --stream
```

Debug sends the local manifest and element files to Sandbox without first saving them as the remote component. In stream mode, live `api.log()` frames go to stderr and the terminal result goes to stdout. A copy of the result is stored under `.revoengine/output/`.

Local JavaScript/TypeScript library components are included as transient overrides by default. Use `--no-extra-libs` when you intentionally want only server-saved active libraries.

For platform 1.8, use a compatible CLI and remove retired library-selection fields from checked-in execution configuration. Follow [Upgrade to 1.8](/developers/upgrading-to-1-8) before pushing existing manifests.
